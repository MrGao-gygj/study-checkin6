# 学习打卡 · H5 主页

手机/电脑都能用的打卡页面：滑动分步填写、自动显示当天日期、提交后进入「打卡墙」总列表，多人实时同步，还有**学习排行榜**。

**一天两次打卡**：早上 **① 定计划**（起床打卡 + 时间段待办清单），晚上 **② 交结果**（逐条勾待办 + 时间分配盘 + 学习成果 + 完成情况 + 就寝时间）。计划与结果分开填写，打卡墙按人自动合并展示，两边都留档。

**排行榜**：按「本周 / 本月 / 全部」统计每个人的**连续打卡天数**、**打卡次数**和**总学习时长**，可切换排名依据（学习时长 / 打卡次数 / 连续天数），前三名有奖牌高亮。

**分享圈（第五个 tab）**：朋友圈式分享——配文 + 最多 3 张图片（自动压缩），**全群可见**、随打卡数据一起同步；自己发的可以删除。

**我的（个人档案）**：按名字独立保存，换名字看的就是那个人的档案：
- **总览**：本周 / 本月 / 全部的出勤天数、学习时长、打卡次数、待办完成率；**学习内容分布轮盘**（按每条待办的「规定时长」跨天汇总）；跨天的**时间盘**（各分类占比）；按周分组的**学习足迹**；
- **相册**：图书馆、笔记、学习桌面照片存档（按名字分开，只存本机 IndexedDB，不随打卡同步）；
- **睡眠**：晚上填就寝时间 + 早上起床打卡 = 每晚睡眠时长，含 7 天平均；
- **语录**：每人一份自定义励志语录，晚上勾待办时随机弹出；全部完成还会弹庆祝卡片。

一套代码同时是**前端页面**和**后端服务**，可直接部署到 Render 免费实例。

## 打卡流程（一天两次）

| 阶段 | 时间 | 填什么 | 步数 |
| --- | --- | --- | --- |
| ① 定计划 | 早上 / 开始学习前 | 姓名、专业、**起床打卡**、**时间段 + 待办清单**（先选时间段再写事项，每条可填**规定时长**）、预计总时长 | 3 步 |
| ② 交结果 | 晚上 / 学习结束后 | 姓名、**逐条勾早上待办**（每勾一条弹励志语录）、**时间分配**（各分类时长 → 时间盘）、实际成果、完成情况、明日计划、就寝时间 | 5 步 |

- 页面顶部卡片可直接切换「① 定计划 / ② 交结果」两个阶段，按钮右上角会显示「已定 / 已交」标记。
- 进入页面时自动判断：**今天还没定计划 → 默认「定计划」；已定计划 → 默认「交结果」**。
- 当天同一人同一阶段重复提交视为**修改**，不会产生重复记录。
- **时间段 + 待办**：预计总时长默认按每条待办的「规定时长」累加（没填就用时间段长度，也可点快捷时长固定）；待办勾选状态在改计划时会尽量保留。
- 勾待办时**完成情况自动判断**（全勾=已完成、勾了一部分=部分完成、没勾=未完成），也可以手动改。
- 时间分配里各分类时长合计就是当晚的实际学习时长（`actualHours`），时间盘实时变化。
- 睡眠统计 = 前一天结果里的就寝时间 + 第二天计划里的起床打卡，在「我的 → 睡眠」里看每晚时长和 7 天平均。
- 打卡墙按「日期 + 姓名」把两次打卡合成一张卡片：显示计划（时间段待办清单 + 勾选进度）和结果（实际时长/成果/完成情况/明日计划）；只交了一边的会标出「待交结果 / 缺计划」。
- 旧版一条记录同时含计划+结果的数据仍能正常显示（自动兼容）。

## 我的（按名字独立的个人档案）

顶部 tab 切到「我的」，先填打卡名字（默认带出上次用的），四个子页——**换名字看到的就是那个人的数据**（总览 / 相册 / 睡眠 / 语录都按名字分开）：

- **📊 总览**：按「本周 / 本月 / 全部」统计出勤天数、学习时长、打卡次数、待办完成率；**学习内容分布轮盘**把每条待办按「规定时长」跨天汇总（没填时长的退回用时间段长度）；时间盘把每晚填的时间分配按分类汇总；**学习足迹**按周分组折叠展示，每天能看到时长、待办勾选明细和完成状态。
- **📷 相册**：选分类（场景/笔记/学习）+ 备注，从手机相册选图上传，自动压缩到长边 1280px 存本机（IndexedDB，超出时降级 localStorage）；照片记归属名字，只显示本人的；点开可看大图、改备注、删除。照片**只存本机**，不随打卡记录同步。
- **🌙 睡眠**：最近 14 晚的就寝/起床/时长列表 + 近 7 天平均值；缺起床打卡的晚上标「待补」。
- **💬 语录**：每人一份、一行一条自定义语录（存 localStorage），勾待办时优先随机抽自己的；内置 15 条兜底，可点按钮试抽。

## 分享圈（第五页 · 全群可见）

顶部 tab 切到「分享」，类似朋友圈：

- **发布**：填名字 + 配文（选填）+ 最多 3 张图片（必有一项），图片自动压缩到长边 900px；发布后**全群同步可见**。
- **信息流**：按时间倒序展示大家的帖子（头像、名字、日期时间、配文、图片）；点图片可放大查看。
- **删除**：只有发布人本人（名字一致）能看到删除按钮。
- **同步**：帖子跟打卡记录走同一个接口（`/api/checkins` 的 `posts` 字段），断网时先存本机、恢复后自动补传。
- 图片以压缩后 base64 存在数据文件里，请适度分享；数据量大时同步会变慢。

## 排行榜（第三页）

底部/顶部 tab 切到「排行榜」，默认展示**本周**榜单：

- **时间范围**：`本周`（周一起算）/ `本月`（1 号起）/ `全部`；打卡次数、出勤天数、学习时长都只统计该时间段内的记录。
- **排名依据**：可切换 `学习时长` / `打卡次数` / `连续天数`，切换后按对应指标重排（同分依次比较另两项，再按姓名稳定排序）。
- **榜单顶部汇总**：参与人数、打卡总次数、合计学习时长（以及人均小时数）。
- **每行信息**：排名（前三名🥇🥈🥉）、头像首字、专业、连续天数、打卡次数、出勤天数，右侧大字为当前排序指标，下方进度条按相对最高值比例展示。
- **统计口径**：
  - 学习时长 = 结果打卡里「实际时长」之和（`actualHours`），计划时长不计入；
  - 打卡次数 = 计划、结果**各算一次**（旧版合并记录算 1 次）；出勤天数 = 当天有任意记录的天数；
  - 连续天数 = 从最近一次打卡往前连续的天数（今天还没打卡则从昨天往前数），按**全部历史**计算，不受时间范围影响；
  - 设置过姓名（`localStorage`）的人会带「我」标记，方便找到自己。
- 无记录时显示空状态；数据更新（远程同步/刷新按钮）后榜单自动重算。

## 同步机制与排错（记录没同步怎么查）

### 保存与重试

- 提交时**先写手机本机**（localStorage），再 `PUT /api/checkins` 传到服务器；成功后右上角显示「已同步」。
- 传输失败时右上角变为「**待同步**」（红点），记录不会丢：之后每 15 秒轮询、切回页面、手机网络恢复时都会**自动补传**；本次会话只弹一次提示，避免刷屏。
- 页面可见时每 15 秒拉取一次全群数据（不再只在打卡墙/排行榜拉取），所以顶部统计也会跟着更新。
- 同一人同一天同一阶段如果因为换设备/清缓存出现重复记录，统计和展示只按**最新一条**算，不会让时长或排名翻倍。

### 三步定位

1. **看页面右上角状态**
   - `已同步`：正常；
   - `待同步`：本地有记录没传上去（会自动重试，保持页面打开 15 秒即可）；
   - `同步失败`：请求到不了后端（多半是没部署后端 / 地址不对 / 域名被拦）；
   - `本机模式`：页面是 `file://` 打开，或 `CONFIG.remote.url` 为空。
2. **打开 `<你的链接>/health`**，对比下面几个字段：

   | 字段 | 正常值 | 说明 |
   | --- | --- | --- |
   | `storage` | `"gist"` | `"file"` 表示没配 Gist，数据在实例重启/休眠后会丢 |
   | `gistReady` | `true` | `false` 表示从 Gist 读取失败 |
   | `lastError` | `null` | 有值就是 Gist 报错（如 `HTTP 401` token 没权限 / 过期，`HTTP 404` Gist ID 错） |
   | `records` | 当前记录数 | 看看那条记录在不在 |
   | `lastSavedAt` | 最近一次落盘时间 | `null` 表示还没成功保存过 |

3. **打开 `<你的链接>/api/checkins`**，直接看服务器上的原始 JSON：如果里面有那条记录，说明数据已到后端，问题在对方页面缓存/没刷新；如果没有，说明请求根本没到服务器。

### 常见原因对照

| 现象 | 最可能原因 | 处理 |
| --- | --- | --- |
| `/health` 里 `storage: "file"` | Render 没填 `GIST_ID` / `GITHUB_TOKEN`（或填了但为空） | 到 Render → Environment 补齐两个变量 → **Manual Deploy** |
| `/health` 里 `lastError: "gist load failed: HTTP 401"` | token 没权限或过期 | 重新生成 token（Gists 读写）→ 更新环境变量 → Manual Deploy |
| `/health` 里 `lastError: "HTTP 404"` | Gist ID 填错 / Gist 被删 | 核对 32 位 ID，重建 Gist |
| 页面角标「同步失败」 | 部署在 GitHub Pages（纯静态，没有 `/api/checkins`） | 按部署教程走 Render，不要只用 Pages |
| 记录只在自己手机上 | 页面处于「本机模式」或请求失败且没等重试 | 确认链接是 `https://...` 且角标显示「已同步」 |
| 记录过一段时间消失 | 存储用了 `file`（实例重启清空） | 配置 Gist 后重启部署 |
| 打卡墙没有但 `/api/checkins` 有 | 对方页面缓存了旧版本 | 关掉页面重进，或链接加 `?v=2` |

> 免费实例冷启动要 30–60 秒，刚打开时 `/health` 也可能暂时失败，等页面加载完再查。

## 本机 / 局域网（零配置）

1. 双击 `启动打卡服务.cmd`
2. 电脑打开 `http://127.0.0.1:8787`
3. 手机连同一 WiFi，打开窗口里显示的 `http://电脑IP:8787`（首次会弹防火墙提示，选「专用网络」允许）

关窗口即停服务；数据存 `server/data.json`，不丢。

## 部署到公网（GitHub + Render 免费）

### 1. 把代码传到 GitHub

1. 登录 GitHub → 右上角 `+` → **New repository**
2. 仓库名填 `study-checkin`，选 Public（或 Private 都行）→ **Create repository**
3. 进入仓库 → **Add file → Upload files**
4. 打开本文件夹（`打卡工具`），把**里面的所有文件和 `server` 文件夹**拖进上传框 → **Commit changes**

> 仓库根目录应该能看到 `index.html`、`server/`、`render.yaml`、`package.json`。

### 2. 建一个 Gist 存打卡数据（Render 免费实例磁盘不持久，用它持久化）

1. 打开 https://gist.github.com → 文件名填 `checkins.json`，内容填：
   ```json
   {"records":[]}
   ```
2. 选 **Create secret gist**
3. 记下地址里的 Gist ID：`https://gist.github.com/你的用户名/`**`32位ID`**

### 3. 建一个 Token（只给 gist 读写权限）

1. 打开 https://github.com/settings/tokens?type=beta → **Generate new token**
2. 名称随意（如 `study-checkin`），有效期选 90 天或 No expiration
3. **Account permissions → Gists → Read and write**
4. 生成后复制 token（只显示一次）

### 4. Render 部署

1. 打开 https://render.com → **Get Started** → 用 GitHub 账号登录并授权
2. 右上角 **New +** → **Blueprint**
3. 选择 `study-checkin` 仓库 → Apply
4. 弹出环境变量时填：
   - `GIST_ID` = 第 2 步的 Gist ID
   - `GITHUB_TOKEN` = 第 3 步的 token
5. **Create** → 等待部署完成（约 1-2 分钟）

> 如果 Blueprint 不认，也可以手动：**New + → Web Service** → 选仓库 →
> Runtime 选 `Node`，Build Command 填 `npm install`，Start Command 填 `node server/server.mjs`，
> Instance Type 选 **Free**，再到 Environment 添加 `GIST_ID`、`GITHUB_TOKEN` 两个变量。

### 5. 拿到链接，发微信群

部署完成后得到 `https://study-checkin-xxxx.onrender.com`：
1. 电脑打开，试提交一次打卡
2. 切到「打卡墙」确认记录出现
3. 用手机打开同一网址确认正常
4. 把链接发到微信群，群成员点开即可同步打卡

> 免费实例 15 分钟无人访问会休眠，再次打开需要 30–60 秒唤醒，属正常现象。

## 配置

`index.html` 顶部 `CONFIG`：

```js
const CONFIG = {
  groupName: '一起学习打卡群',   // 群名
  remote: {
    url: location.protocol === 'file:' ? '' : '/api/checkins',  // 共享后端地址
    pollInterval: 15000          // 自动刷新间隔（毫秒）
  }
};
```

- 同域部署（本项目）：保持默认即可。
- 前后端分离：改成完整地址，如 `https://api.example.com/api/checkins`。
- 双击打开文件（file://）：自动进入本机模式。

接口约定（接自己的后端时照此实现）：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/checkins` | 返回 `{"records":[...],"posts":[...]}` |
| PUT | `/api/checkins` | 提交 `{"records":[...],"posts":[...]}`，各自按 id 合并保存（可只传其一） |
| GET | `/health` | 健康检查 |

## 数据字段

数据库里每天每人最多两条记录，用 `phase` 区分阶段：

```json
// ① 计划打卡
{
  "id": "唯一ID",
  "date": "2026-10-27",
  "name": "张三",
  "major": "计算机",
  "phase": "plan",
  "planHours": 4,
  "planTask": "概率论第 3 章；英语真题一套",
  "todos": [
    { "s": "09:00", "e": "11:00", "text": "概率论第 3 章", "dur": 2, "done": true },
    { "s": "14:00", "e": "16:00", "text": "英语真题一套", "dur": 1.5, "done": false }
  ],
  "wakeTime": "07:50",
  "time": "08:30",
  "createdAt": 1761570000000
}
```

```json
// ② 结果打卡
{
  "id": "唯一ID",
  "date": "2026-10-27",
  "name": "张三",
  "major": "计算机",
  "phase": "result",
  "actualHours": 4,
  "alloc": [
    { "cat": "概率论", "h": 2.5 },
    { "cat": "英语", "h": 1.5 }
  ],
  "task": "做完第 3 章前 5 节，正确率 85%",
  "status": "已完成 | 部分完成 | 未完成",
  "tomorrow": "线代第 2 章 + 错题复盘",
  "bedtime": "23:30",
  "time": "21:30",
  "createdAt": 1761575400000
}
```

```json
// ③ 分享帖（posts 数组，与 records 同接口同步）
{
  "id": "唯一ID",
  "date": "2026-10-27",
  "time": "12:30",
  "ts": 1761575400000,
  "name": "张三",
  "text": "今天在图书馆三楼刷题",
  "images": ["data:image/jpeg;base64,..."]
}
```

- `todos`：早上列的时间段待办（`dur` 为规定完成时长，`done` 由晚上勾选写回）；旧记录没有 `todos` 时回退显示 `planTask`。「我的 → 总览」的学习内容轮盘按 `dur`（缺省用时间段长度）跨天汇总。
- `alloc`：时间分配（分类 + 小时），合计即 `actualHours`；「我的 → 总览」按分类跨天汇总成时间盘。
- `wakeTime` / `bedtime`：起床打卡与就寝时间，用于「我的 → 睡眠」统计（前一天就寝 + 第二天起床 = 一晚时长）。
- `posts`：分享圈帖子，与 records 一起 GET/PUT 同步；图片为压缩后的 base64。

> 兼容旧数据：没有 `phase` 字段的旧记录（一条里同时含 `planHours` / `actualHours` / `task` / `status`）会被当作「计划 + 结果」合并显示，不影响已有打卡。
